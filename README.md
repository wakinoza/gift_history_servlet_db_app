# 頂き物情報管理 Webアプリケーション - Spring Bootリファクタリング版

本プロジェクトは、以前サーブレット/JSP環境で開発した「単体テスト更新版」をベースに、Spring Boot / Spring Security / Spring Data JPAを用いてフルリファクタリングを行い、さらにDocker（環境変数・ヘルスチェック完全対応）によるコンテナ環境へと進化させたアップデート版です。

堅牢なセキュリティの確立と、前作に引き続きJaCoCoによるテスト網羅率（カバレッジ）100%を達成し、実務水準の品質と運用性を担保しました。

## 🛠️ 開発の内容（前作からの進化・リファクタリング）

単なるフレームワークの置き換えにとどまらず、Springエコシステムの強みを最大限に活かしたリファクタリングと、実務で重要視されるセキュリティ・運用アンチパターンの排除を行いました。

*   **🛡️ 認証・認可の統合管理（Spring Security）**
    *   未認証ユーザーが主要URL（`/gift/main`や`/gift/new`など）へ直接アクセスした場合、自動的にログイン画面（`/login`）へ強制リダイレクトする安全なアクセス制御を確立しました。
*   **🔌 本番用プロパティとテスト用プロパティの完全分離**
    *   `application.properties`を本番用とテスト用（`test.properties`）に完全に分離。テスト実行時にはH2インメモリデータベース（MySQL互換モード）へ自動切り替えする安全なテスト環境を構築しました。
*   **🚦 画面崩れのない親切な「404 専用エラー画面」の導入**
    *   存在しないID（例: `/gift/detail/99999`）への直接アクセスに対し、冷たいシステムエラー画面（Whitelabel Error Page）を見せず、共通レイアウト（ヘッダー・フッター等）を維持した専用の `error/404.html` へ着地させ、ユーザーを安全にメイン画面へ誘導する設計を導入しました。
*   **🌿 網羅率100%の継続達成と可読性の高いテスト構成**
    *   JUnit 5 / Mockito / AssertJ を用い、Controller、Serviceの各レイヤーで正常系・異常系の全ルートを検証。JaCoCoカバレッジ100%を達成しました。

## 🚀 Dockerの起動手順

Dockerがインストールされた環境であれば、環境の差異を受けず、以下の手順ですぐに動作確認が可能です。

### 1. リポジトリをクローン
以下のコマンドを実行してください。

```bash
git clone https://github.com/wakinoza/gift_history_app
cd gift_history_app
```

### 2. 環境変数の準備
.env.example をコピーして .env を作成し、必要な値を設定してください。（※ .env は .gitignore に登録され、安全に隠蔽されています）

### 3. コンテナの起動
compose.yml には healthcheck を導入しており、MySQLの完全な起動を待ってからSpring Bootが立ち上がる安全な順序制御を行っています。

```bash
docker compose up -d --build
```

### 4. アプリの確認
ブラウザで「http://localhost:8080/login」 にアクセスしてください。

ユーザー名：yamada / パスワード：yamada_password でログイン可能です。

### 5. テストの実行（Maven）
インメモリDBに自動接続され、ローカル環境を汚さずに高速にテストが実行されます。

```bash
mvn test
```

## 🧠 開発で難しかった点（技術的葛藤）

### テストの網羅性とメソッドの出口（return）に関する設計のトレードオフ
前作のサーブレット版では「早期リターンが多発して複雑化したロジックを1つに整理する（出口を減らす）」リファクタリングを行いました。これは構造化プログラミングの基本原則に則ったアプローチでした。

しかし、今回のSpring Bootへの移行に伴い、多くの業務バリデーションやステータス判定が絡む複雑なメソッドを実装する際、前作同様に出口を1つに絞ろうとすると、逆に条件分岐のネストが深く絡み合い、JaCoCoでのカバレッジ100%を網羅するためのテストケースが指数関数的に膨れ上がってしまうという壁に直面しました。

---

## 💡 得られた教訓

### 「原則に囚われすぎず、テスト容易性と可読性のバランスを取る」重要性
この課題に対し、あえて前作とは逆のアプローチである「ガード節（Early Return）を用いて不適合条件を即座に弾き、メソッドの出口を増やす」リファクタリングを行いました。

その結果、判定ロジック自体のネストが劇的に浅くなり、コードの可読性が向上しただけでなく、テストコードの複雑度を大幅に下げることに成功しました。

「出口は少ない方が良い」という一般的な原則に盲従するのではなく、目の前のドメインロジックの複雑さやテスト容易性（Testability）に応じて、柔軟に設計の引き出しを使い分ける柔軟性が実務の品質向上には不可欠である、と学ぶ貴重な経験となりました。
